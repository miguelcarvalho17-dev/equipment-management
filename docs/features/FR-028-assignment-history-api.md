# FR-028 Assignment History API

## Purpose
Read-only Business Central API v1.0 entity `assignments` on table 50103 "EQM Equipment Assignment" (FR-004, FR-005, FR-006), so reporting and analytics platforms can read equipment movements (who had which equipment, from when to when) without database access (GitHub issue #66). It follows the API conventions C1 to C10 in `docs/features/FR-026-equipment-api.md`.

Status: implemented and merged to `main` (PR #117, closes #66). App version stays 29.0.0.0. No new table, field, upgrade code or event.

## Endpoint
`/api/miguelCarvalho/equipment/v1.0/companies({companyId})/assignments` and `.../assignments({id})`, where `{id}` is the `id` (SystemId) field. Entity `assignment`, entity set `assignments`, `ODataKeyFields = SystemId`.

## Fields
All read-only (page `Editable = false`).

| API field | Table field |
|---|---|
| `id` | SystemId |
| `entryNumber` | Entry No. |
| `equipmentNumber` | Equipment No. |
| `employeeNumber` | Employee No. |
| `assignmentDate` | Assignment Date |
| `status` | Status (enum `Active` / `Closed`) |
| `closingDate` | Closing Date |
| `lastModifiedDateTime` | SystemModifiedAt |

`assignedBy` and `closedBy` (BC user names) are deliberately not exposed: they are personal data (EndUserIdentifiableInformation) and the feed is for equipment movements. They could be added later in v1.0 as an additive change; removing them later would be breaking.

## Behavior
- Returns **all** entries, active and closed. Filter with `$filter=status eq 'Closed'`, `$filter=equipmentNumber eq 'X'`, `$filter=employeeNumber eq 'X'`, or `$filter=lastModifiedDateTime gt <datetime>` for incremental sync. `$orderby=entryNumber` gives chronological order.
- Relationships are plain codes. Join `equipmentNumber` with `equipments` (FR-026) on the client; no description or employee name is exposed.
- GET only. The page sets `InsertAllowed`, `ModifyAllowed`, `DeleteAllowed` and `Editable` to false and `DataAccessIntent = ReadOnly`. POST, PATCH and DELETE are expected to be rejected; the HTTP status is **not verified** (V1). Entries are still created and closed only by the app (assign and return). No page triggers or procedures. `Extensible = false`.
- `DataAccessIntent = ReadOnly` may read from a replica, so a just-closed entry can appear with a short delay.

## Test status
Codeunit 50182 (`test/src/EQMAssignmentAPITests.Codeunit.al`, AutoRollback), 7 tests, **all pass in AL-Go CI (PR #117)**. The first CI run passed 7 of 8; the 8th (`ClosedEntryIsUnchangedAfterRejectedModify`) failed because `Modify` is not allowed inside a TryFunction during `RunTests`, so it was removed; the re-run was green:
- `EquipmentFilterReturnsClosedAndActiveEntries`, `EquipmentFilterExcludesOtherEquipment` (equivalent of `$filter=equipmentNumber eq`)
- `StatusFilterSeparatesClosedAndActive` (equivalent of `$filter=status eq`)
- `EntryIsFoundBySystemId`, `UnknownSystemIdIsNotFound` (equivalent of `assignments({id})`)
- `ReturnKeepsSystemIdAndClosesEntry` (SystemId stays, status closes, relevant for `lastModifiedDateTime` sync)
- `ClosedEntryCannotBeModified` (history stays immutable)

No HTTP calls (CI containers cannot authenticate them, see FR-026). Plan scenarios 6 to 11 are manual sandbox checks, not done.
