## Goal
When a warranty is about to end, the system creates an alert 90, 60 and 30 days before the Warranty End Date, so users
can plan a renewal, schedule a replacement or raise a warranty claim in time. Alerts are records that a daily job
queue entry (or a user, with an action) creates; each interval fires once per equipment and warranty end date, and
fires again when the end date is changed. Users see the open alerts in a new Warranty Alerts list, in a new dashboard
tile and from the Equipment Card, and acknowledge them when they have acted.

### Requirement restated
- WA-R1 Generate alerts for equipment whose warranty is approaching its end.
- WA-R2 Alert intervals: 90, 60 and 30 days remaining.
- WA-R3 Purpose: plan renewals, schedule replacements, raise claims before the end date (users must be able to find and
  work through the alerts).
- Caller requirements: each interval fires once per equipment warranty; a changed end date re-arms the intervals.

### Interpretation (defaults, see Q1-Q12)
- **Days remaining** = Warranty End Date - reference date (D - T). The reference date is `Today()`, as in FR-015 Q1. A
  warranty that ends today has 0 days remaining and is still covered (FR-015 Q2), so it can still raise the 30-day
  alert. A warranty with D < T (Expired in FR-015) never raises a new alert.
- **Which interval is due:** the smallest interval N in (30, 60, 90) with days remaining <= N. 0..30 days -> 30-day
  interval; 31..60 -> 60-day; 61..90 -> 90-day; more than 90 -> none.
- **Catch-up (Q2):** only the due interval is created. Equipment registered (or a job that did not run) with 45 days left
  gets the 60-day alert only; the 90-day alert is skipped, not created late. The 30-day alert follows when 30 days are
  left.
- **Once per interval:** an alert is identified by (Equipment No., Warranty End Date, Alert Interval). A new alert is
  created only when no Open or Acknowledged alert with the same three values exists. Cancelled alerts do not count.
- **Re-arm:** the Warranty End Date is copied into the alert. When the equipment's end date changes, the old open alerts
  are cancelled on the next run (Q3) and the new date has no alerts yet, so every interval can fire again. Changing the
  date back to an older value re-arms it too, unless an alert for that date was Acknowledged (it was already handled).
- **Equipment in scope:** equipment with a Warranty End Date, status not Lost or Disposed (same rule as the FR-015
  tiles). Warranty Start Date is ignored (FR-015 Q4).
- **Generation (Q1):** a codeunit that the standard job queue runs once a day; the same logic runs from a "Generate
  Alerts" action on the Warranty Alerts page. Running it twice on one day creates nothing new.
- **Surfacing (Q4):** new list page "Warranty Alerts" (Tell Me, Role Center, Equipment Card navigation), a new tile
  "Open Warranty Alerts" in the dashboard's Warranty tile group. No notification, no email.

## Approach and rejected alternatives
- Chosen: **stored alert records created by a daily job queue codeunit, with a manual action that runs the same logic.**
  A new table "EQM Warranty Alert" keeps one row per fired interval with a snapshot of the end date and a status (Open,
  Acknowledged, Cancelled). An internal codeunit "EQM Warranty Alert Mgt." cancels stale open alerts and creates the due
  ones; a thin public codeunit "EQM Warranty Alert Job" (`TableNo = "Job Queue Entry"`) calls it from the job queue.
  Storing the alert is the only way to know that an interval already fired and to let users acknowledge it.
- Rejected: **calculate on read** (the FR-015 approach, for example a "Days to Expiry" column or tiles per interval).
  It cannot remember that an interval fired, cannot be acknowledged and cannot "fire once"; the caller's
  once-per-interval and re-arm requirements need state.
- Rejected: **generate when a page opens** (Role Center, cue part, Equipment List). Writes on page open need Insert
  permission for every reader, run the scan for every user many times a day, and create nothing when nobody opens the
  page. The manual action covers the "now" case.
- Rejected: **stored "Last Alert Interval" field on table 50100.** It needs an upgrade-free schema change on the main
  table, every update runs the equipment `OnModify` consistency checks and assignment logic, it keeps no history and no
  acknowledgement, and the job user would need Modify on equipment.
- Rejected: **a unique key on (Equipment No., Warranty End Date, Alert Interval).** It would block re-arming when a
  date is changed back after a cancellation. Uniqueness is checked in code against Open and Acknowledged alerts, under a
  table lock.
- Rejected: **creating the 90/60 alerts late (catch-up of every missed interval).** A warranty registered with 20 days
  left would get three alerts at once with the same action needed (Q2).
- Rejected: **scheduling the job queue entry from code (install or a setup action).** It writes to the standard Job
  Queue Entry table and needs a base app API whose exact names are not verified here (no guessing). The help explains how
  an administrator creates the entry (Q6).
- Rejected: **notification or email per alert.** Not requested; emails need email account setup and personal
  recipients. Follow-ups (Q4).
- Rejected: **a setup table or fields for the intervals.** The issue fixes 90/60/30; the intervals are an enum plus one
  procedure, so a setup can be added later without a breaking change (Q5).
- Rejected: **one codeunit for both the job and the logic.** The job codeunit must be runnable by the job queue by ID
  (keep it public, Q9 verify item); the logic stays `Access = Internal` so it is not a public API.

### Codeunit 50110 "EQM Warranty Alert Mgt." (new)
`Access = Internal`. XML summary: "Creates, cancels and acknowledges warranty alerts." All procedures `internal`
unless stated `local`, each with an XML doc comment.

Labels (all on this codeunit):
- `NothingToAcknowledgeErr`: 'The selected warranty alerts are already acknowledged or cancelled.' (no placeholder)
- Telemetry, all `Locked = true`: `AlertsGeneratedTelemetryTok` = 'EQM0001' (event ID), `AlertsGeneratedTelemetryMsg`
  = 'Warranty alerts generated.', `ScheduledTok` = 'JobQueue', `ManualTok` = 'Manual'. Dimension name tokens (locked):
  'AlertsCreated', 'AlertsCancelled', 'ReferenceDate', 'Trigger'.

Procedures:
1. `GetIntervalDays(AlertInterval: Enum "EQM Warranty Alert Interval"): Integer` - case: "30 Days" -> 30, "60 Days" ->
   60, "90 Days" -> 90. No else branch is reachable (enum not extensible); use `else exit(0)` to satisfy the compiler.
   Doc: "Returns the number of days before the warranty end date at which the interval is due."
2. `GetLongestIntervalDays(): Integer` - returns `GetIntervalDays("90 Days")`.
3. `FindDueInterval(DaysRemaining: Integer; var AlertInterval: Enum "EQM Warranty Alert Interval"): Boolean` -
   when DaysRemaining < 0 or > `GetLongestIntervalDays()`: exit(false). Otherwise check, in this order, "30 Days",
   "60 Days", "90 Days": the first with DaysRemaining <= `GetIntervalDays(<value>)` is assigned and exit(true).
   Doc: "Finds the most urgent interval that is due for the number of days left. False when the warranty has ended or is
   more than 90 days away."
4. `GenerateAlerts(ReferenceDate: Date; IsScheduled: Boolean; var CreatedCount: Integer; var CancelledCount: Integer)`
   in this order:
   1. CreatedCount := 0; CancelledCount := 0. When ReferenceDate = 0D: ReferenceDate := `Today()`.
   2. `WarrantyAlert.LockTable()` (prevents two runs creating duplicates; documented reason, no `Commit`).
   3. CancelledCount := `CancelStaleAlerts()`.
   4. Equipment: `SetLoadFields("No.", "Warranty End Date", Status)`; `SetRange("Warranty End Date", ReferenceDate,
      ReferenceDate + GetLongestIntervalDays())` (excludes blank and past dates); `FindSet()`. For each record:
      - skip when `Equipment.IsFinalStatus(Equipment.Status)`;
      - skip unless `Equipment.CalcWarrantyStatus(ReferenceDate)` is Active or "Expiring Soon" (FR-015 reuse; guard);
      - DaysRemaining := `Equipment.GetWarrantyDaysRemaining(ReferenceDate)`;
      - skip unless `FindDueInterval(DaysRemaining, AlertInterval)`;
      - skip when `AlertExists(Equipment."No.", Equipment."Warranty End Date", AlertInterval)`;
      - otherwise `CreateAlert(Equipment, AlertInterval, ReferenceDate)` and CreatedCount += 1.
   5. `LogGenerationTelemetry(ReferenceDate, IsScheduled, CreatedCount, CancelledCount)`.
   No `Message`, no `Confirm`, no `Commit` in this procedure (it runs in the job queue).
   Doc: "Cancels open alerts that no longer apply and creates the due alert for each piece of equipment whose warranty
   ends within 90 days of the reference date. Each interval is created once per equipment and warranty end date. 0D
   means today."
5. `local procedure CancelStaleAlerts(): Integer` - WarrantyAlert `SetRange(Status, Open)`; `SetLoadFields("Equipment
   No.", "Warranty End Date", Status)`; `FindSet()`. For each: Equipment `SetLoadFields("Warranty End Date", Status)`;
   cancel when `not Equipment.Get(No.)`, or Equipment."Warranty End Date" <> alert."Warranty End Date", or
   `Equipment.IsFinalStatus(Equipment.Status)`. Cancel = on a second record variable `Get(Entry No.)`, Status :=
   Cancelled, "Cancelled At" := `CurrentDateTime()`, `Modify(false)` (no triggers on the table). Returns the count.
   Open alerts of a warranty that has simply expired (date unchanged) are **not** cancelled.
6. `local procedure AlertExists(EquipmentNo: Code[20]; WarrantyEndDate: Date; AlertInterval: Enum ...): Boolean` -
   `SetCurrentKey("Equipment No.", "Warranty End Date", "Alert Interval")`, SetRange on the three fields, `SetFilter
   (Status, '<>%1', Cancelled)`, exit(not IsEmpty()).
7. `local procedure CreateAlert(Equipment: Record "EQM Equipment"; AlertInterval: Enum ...; ReferenceDate: Date)` -
   `Init()`, "Equipment No.", "Alert Interval", "Warranty End Date" := Equipment's, "Alert Date" := ReferenceDate,
   Status := Open, `Insert(true)` (Entry No. by AutoIncrement; do not set it).
8. `AcknowledgeAlerts(var WarrantyAlert: Record "EQM Warranty Alert"): Integer` - on the caller's filtered set:
   add `SetRange(Status, Open)`; when `IsEmpty()`: `Error(NothingToAcknowledgeErr)`. `FindSet()`; for each: on a second
   record variable `Get(Entry No.)` (the loop record is filtered on Status = Open, so it is not modified), then Status
   := Acknowledged, "Acknowledged By" := `CopyStr(UserId(), 1, 50)`, "Acknowledged At" := `CurrentDateTime()`,
   `Modify(true)` on that second record. Restore the caller's Status filter afterwards (save it with `GetFilter` before, set it back after).
   Returns the count. Doc: "Acknowledges the open alerts in the filter. Acknowledged and cancelled alerts are skipped.
   Raises an error when no open alert is in the filter."
9. `local procedure LogGenerationTelemetry(...)` - builds the dictionary (AlertsCreated, AlertsCancelled as
   `Format(..., 0, 9)`, ReferenceDate as `Format(ReferenceDate, 0, 9)`, Trigger = ScheduledTok or ManualTok) and calls
   `Session.LogMessage(AlertsGeneratedTelemetryTok, AlertsGeneratedTelemetryMsg, Verbosity::Normal,
   DataClassification::SystemMetadata, TelemetryScope::All, Dimensions)`. No equipment numbers, descriptions or user
   names in telemetry.

## Test scenarios
**No automated tests in this iteration** (Q12 default, as in FR-003 to FR-015). Test codeunit 50170 "EQM Warranty

Test data, unless stated: active category LAPTOP; equipment saved with `Insert(true)`, Status Available. R = a fixed
reference date (for example 15 June 2026). Generator tests call `GenerateAlerts(R, false, Created, Cancelled)`.
"Alert(E, N, D)" means an alert for equipment E, interval N days, Warranty End Date D.

Interval rule (`FindDueInterval`, `GetIntervalDays`)
- WA1 `GetIntervalDays` returns 30, 60, 90 for the three values; `GetLongestIntervalDays` returns 90.
- WA2 Days remaining 0, 1, 30 -> "30 Days"; 31, 60 -> "60 Days"; 61, 90 -> "90 Days" (boundaries).
- WA3 (negative) Days remaining -1 and 91 -> returns false.
- WA4 `GetWarrantyDaysRemaining(R)`: End = R + 45 -> 45; End = R -> 0; End = R - 3 -> -3; no end date -> 0.

Generation
- WA5 Given E1 End = R + 90, when generated, then exactly one Alert(E1, 90, R + 90) with Status Open and Alert Date R;
  Created = 1.
- WA6 Given E2 End = R + 61, then Alert(E2, 90); given E3 End = R + 60, then Alert(E3, 60); given E4 End = R + 30, then
  Alert(E4, 30); given E5 End = R, then Alert(E5, 30).
- WA7 (negative) Given E6 End = R + 91, E7 End = R - 1, E8 no end date, then no alert for any of them.
- WA8 (once) Given WA5 done, when generated again on R, then no new alert; Created = 0.
- WA9 (progression) Given Alert(E1, 90) exists, when generated on R + 30 (60 days left), then Alert(E1, 60) is added;
  on R + 60 (30 left), Alert(E1, 30) is added; E1 ends up with exactly three alerts, the earlier ones still Open.
- WA10 (catch-up, Q2) Given E9 End = R + 45 and no alerts, when generated, then only Alert(E9, 60); no 90-day alert is
  ever created for that end date (also not on later runs).
- WA11 (acknowledged blocks) Given Alert(E1, 90) Acknowledged, when generated on R, then no new 90-day alert.
- WA12 (re-arm) Given Alert(E1, 90, R + 90) Open, when E1's end date is changed to R + 85 and generated, then the old
  alert is Cancelled with "Cancelled At" filled, Alert(E1, 90, R + 85) is created Open; Created = 1, Cancelled = 1.
- WA13 (re-arm back) Given WA12 done, when the end date is changed back to R + 90 and generated, then Alert(E1, 90,
  R + 85) is Cancelled and a new Open Alert(E1, 90, R + 90) is created (the earlier cancelled one does not block).
- WA14 Given Alert(E1, 90, R + 90) Open, when the end date is cleared and generated, then the alert is Cancelled and no
  alert is created.
- WA15 (Lost/Disposed) Given E10 Disposed with End = R + 20, then no alert; given Alert(E11, 30) Open and E11 then set to
  Lost, when generated, then the alert is Cancelled.
- WA16 Given Alert(E12, 30, R + 10) Open, when E12 is deleted (never assigned) and generated, then the alert is
  Cancelled.
- WA17 (negative) Given Alert(E13, 30, R + 5) Open and the end date unchanged, when generated on R + 6 (expired), then

- WA18 Given E14 Assigned and E15 In Maintenance, both End = R + 20, then both get Alert(_, 30).

## Risks and open questions
Open questions (each has the default used in this plan; answer to change it):
- **Q1 Generation mechanism.** Default: stored alerts, daily job queue codeunit 50111 plus a manual Generate Alerts
  action. Alternative: calculated "alert level" on read with no records (no acknowledge, no fire-once). **Changes the
  whole design.**
- **Q2 Catch-up of missed intervals.** Default: only the most urgent due interval is created (45 days left -> 60-day
  alert only). Alternative: create every interval not yet fired (45 days left -> 90 and 60 at once). **Changes
  GenerateAlerts and WA9/WA10.**
- **Q3 What cancels an open alert.** Default: end date changed or cleared, equipment Lost/Disposed, equipment deleted.
  An open alert of a warranty that expired stays Open. Alternatives: also cancel older open intervals when a more
  urgent one is created (less clutter: one open alert per warranty), or cancel open alerts once the warranty expired.
  **Changes CancelStaleAlerts, WA9, WA17.**
- **Q4 Surfacing.** Default: list page, dashboard tile, card and Role Center actions. Not built: a notification on the
  Role Center or Equipment Card ("3 warranty alerts are open"), email to a responsible user, alert styles (30 days in
  red), a FactBox. Notification and email change the design (email needs recipients and email setup).
- **Q5 Intervals fixed.** Default: 90/60/30 as a non-extensible enum. Alternative: setup fields on table 50102, or an
  extensible enum so partners add intervals (then `GetIntervalDays` needs an interface or event).
- **Q6 Job queue entry creation.** Default: the administrator creates it by hand (help article). Alternative: an action
  on Equipment Setup that creates or opens the entry; needs the standard job queue API names verified (al-event-finder /
  symbol check) and Job Queue Entry write permission.
- **Q7 Job user permissions.** Default: the job runs as a user with EQM - Manager. Alternative: a new small permission set
  "EQM - Alert Job" (R on equipment, RIM on alerts, X on 50110/50111) for a dedicated job user (ID 50104).
- **Q8 Retention.** Default: alerts are never deleted (no Delete permission). Alternative: Administrator Delete, or a
  retention policy registration for table 50107.
- **Q9 Reference date.** Default: `Today()` (FR-015 Q1), also in the job session. Alternative: `WorkDate()`.
- **Q10 Extensibility.** Default: table 50107 Public, no custom event; partners use the table's insert event.
  Alternative: publish `OnAfterCreateWarrantyAlert(WarrantyAlert)` on a public codeunit (becomes a permanent contract).
- **Q11 Telemetry scope.** Default: `TelemetryScope::All` with counts only. Alternative: `ExtensionPublisher` only (needs
  `applicationInsightsConnectionString`, still missing) or no telemetry.
- **Q12 Automated tests.** Default: deferred as in FR-003 to FR-015; test codeunit 50170 reserved, tester step skipped,
  WA-SB1 to WA-SB12 are the verification.

Risks:
- R1 Alerts are only as fresh as the last run: if no job queue entry is set up, no alert appears until a Manager uses
  Generate Alerts. Mitigation: help article, Generate Alerts action, tile visible on the Role Center.
- R2 `Today()` in a job queue session may use a different time zone than the users; an alert can appear a day early or
  late. Accepted (WA-SB5 records it).
- R3 Between an end date change and the next run, the old alert stays Open and no new alert exists. Accepted; Generate
  Alerts refreshes at once.
- R4 Changing an end date back to a value whose alert was Acknowledged does not re-fire that interval (by design).
- R5 `LockTable` on table 50107 serializes concurrent runs (job plus manual); a manual run waits for the job. Accepted;
  runs are short.
- R6 Codeunit 50111's ID and table 50107's fields and both enums become permanent at the first release; settle Q2, Q3,
  Q5 and Q10 now.
- R7 Deleted equipment leaves cancelled alerts with an equipment number that no longer exists (blank description).
  Accepted to keep history; an `OnDelete` cleanup would need Delete permission.
- R8 No automated tests (Q12): regressions are caught only by review and the sandbox checks.
